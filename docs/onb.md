# ONB coverage

The library supports the standard ONB173, ONB179, ONB191, ONB233 and ONB431
domains through `dstu4145.ParamsByName("DSTU_ONB_173")` and the corresponding
named OIDs. `AllParams` now includes fifteen domains: ten PB and five ONB.
Existing PB names and OIDs are unchanged.

## Representation and supported paths

Arithmetic and the coordinates stored in `ec.Curve`/`ec.Point` use polynomial
basis. Each ONB curve has an immutable conversion matrix built from its public
normal-basis root; the inverse is computed by binary Gaussian elimination.
`Curve.DecodeField` and `EncodeField` cross this boundary and reject values
outside the field. Scalars and signature integers are never basis-converted.

ONB conversion applies to the B coefficient and public points, compression/expansion,
digest interpretation, the field product before signature truncation, and
cofactor shared-secret output. The A coefficient remains the integer 0 or 1.
Complete domain comparisons include the basis,
polynomial, coefficients, subgroup order, cofactor and generator. Matching only
field degree and order can silently serialize ONB as PB: some domains share both.

Compressed points now place `Tr(y/x)` at bit `m-1` for ONB, matching the pinned
IIT provider. PB continues to use bit 0. This changes serialized ONB public keys,
certificate key identifiers and signed/encrypted artifacts compared with earlier
library output. Old bit-0 ONB public-point encodings are not automatically retried:
some bytes are valid in both profiles and can identify different points. Regenerate
affected synthetic certificates/requests. Private scalar encodings are unchanged.
The published Cryptonite explicit-domain constants remain recognized by their
complete built-in domain, including the exact legacy generator encoding; this
does not enable legacy decoding of arbitrary public keys.

Supported application paths include named/complete explicit parameters,
little-endian GOST ONB PKCS#8, Key-6/PFX protection and import, certificate key
association, GOST CMS signing/verification, GOST CSR generation/verification and
GOST agreement/encryption. The zero-digest substitute is polynomial-basis one:
conversion occurs before the zero check, covered by independent zero-digest vectors.
PKCS#8 and certificate loaders reject an algorithm/basis mismatch. Embedded
certificates retain the usual discovery-only trust policy.

Explicit Kupyna-256/512 CMS signing and Kalyna CFB/OFB with explicit standard DH
now support GOST ONB certificates. Named ONB certificates and CSRs also support
Kupyna-256/512 signatures while retaining the GOST ONB SPKI algorithm. Alternate
modern SPKI identifiers and ONB cofactor-Kupyna agreement remain rejected. Passing the
primitive tests does not enable arbitrary ONB degrees or nonstandard domains.
These routines do not claim constant-time operation or a completed security review.

## Independent evidence

Public domains and conversion roots come from
[Cryptonite](https://github.com/privat-it/cryptonite/tree/3618d340d22e27a6becf97d89c453f8e64068a39),
specifically `dstu4145_params_internal.c` and PKIX `aid.c`/`oids.h`.
The retained license is in [licenses/cryptonite.txt](licenses/cryptonite.txt).

- `pkg/ec/normal_basis_test.go` checks published conversion values from
  Cryptonite's `utest_dstu4145.c`, inverse maps, normal-basis squaring rotations,
  domain/subgroup order, and point compression including the zero-x point.
- `pkg/dstu4145/testdata/onb-operations-cryptonite.json` was generated by compiling
  that unmodified Cryptonite revision with Ubuntu GCC and invoking its public
  APIs. For all five curves it contains public points, compressed points,
  cofactor shared secrets and signatures. The public scalars are deliberately
  `d=2` and peer `d=7`; the public seed is bytes `00..27`. Cryptonite's PRNG
  also mixes the clock, so rerunning the original producer can change signature
  bytes. The new PB producer freezes that clock explicitly; see
  [primitive fixture reproduction](primitive-validation.md#reproduction).
- `TestONBCryptoniteOperations` verifies those signatures and reproduces them in
  Go with their recovered public nonce, as well as checking the independent
  points and shared secrets. `onb-zero-digest-cryptonite.json` covers the zero-digest
  fallback with the same public keys and source revision. These keys must never
  be used operationally.
  The pinned Cryptonite compressor uses bit 0 for ONB. Tests retain its original
  bytes and compare them through an explicit test-only conversion; they do not
  claim those compressed values are the IIT wire profile.
- `TestONBApplicationRoundtrip` covers GOST CMS, dynamic/static encryption, PFX,
  explicit trust and rejection of unverified modern profiles. This is local
  integration evidence, separate from provider interoperability.
- GOST CSR checks use independent Cryptonite hashing/signature verification and
  OpenSSL request parsing; see [CSR evidence and limits](csr.md).

## Native certificate/CMS evidence

Checks use IIT x86 `1.3.1.224`, SHA256
`475539dd6b01015e73cf3d143783c3f164c3f9db1e92e724c6f6493f086d9f4f`.
On 3 November 2026 the bit-0 selector was identified as a public-key binding
mismatch. `EUGetKeyInfoBinary`, given only a Key-6 scalar container, independently
derives a key identifier matching GOST34311 over the DER OCTET STRING of the
little-endian point with the selector at `m-1`. All five curves matched for
public scalars 1, 2, 7 and a full-width fixture. Ordinary tests retain five native
full-width identifiers in `pkg/dstu4145/onb_iit_test.go`; no SDK is needed to replay
them. The public full-width scalar is `2^(bitlen(n)-2) + 0x12345`.

`TestIITONBNamedCertificates` is a strict positive integration matrix, enabled by
the usual native adapter configuration. It covers all five ONB curves with
named-curve/DKE certificates and four full-width public scalars (the preceding
value plus `i*0x13579`, i=0..3). It requires matching key identifiers, certificate
parsing, Go CMS verified by IIT and IIT CMS verified by Go, both attached and
detached, with modified-content rejection. Two complete runs passed: 20 identities
and 40 signing-mode cases per run. Native errors fail this test.

Synthetic explicit-parameter ONB certificates remain outside that passing
profile: parsing succeeds but signing/verification return native errors 50/51.
Certificates made with tiny public scalars 1, 2 and 7 also returned error 50 on
both ONB173 and the PB257 control; scalar 123456789 passed on both. The reason
for that provider restriction is not established. No real credentials, network
services or external submissions were used. These mathematical fixture checks
do not establish production trust, revocation status or CA acceptance.

`TestIITONBDiagnostic`, opt-in with `IIT_ONB_DIAGNOSTIC=1`, retains the explicit
versus named comparison. PB257 and named ONB checks must pass. Known explicit
ONB rejections remain diagnostic results, not positive interoperability evidence.

The full isolated native regression runner passed after this correction. A
three-minute `FuzzCurveEncodings` campaign with two workers passed 228,073
executions, including selector-only and finite zero-x seeds for all fifteen
domains. The independent CSR check also passed after explicit wire transcoding
in its reference adapter; see [CSR validation](csr.md).

## Kupyna CMS profile

CMS accepts explicit Kupyna-256 and Kupyna-512 digests with supported GOST ONB
certificates. Automatic digest selection still follows the certificate's GOST
public-key algorithm. ONB signature OIDs are `1.2.804.2.1.1.1.1.3.6.1.2` and
`1.2.804.2.1.1.1.1.3.6.3.2`, from the
[official OID registry](https://cip.gov.ua/ua/news/perelik-ob-yektnikh-identifikatoriv-algoritmiv-kriptografichnogo-zakhistu-informaciyi-kriptografichnikh-protokoliv-ta-politik-sertifikaciyi-z-yikh-vikoristannyam).

`TestIITONBKupynaCMS` verifies Go-produced CMS with IIT on all five curves, both
digests and attached/detached content (20 cases). It also checks independent
native signatures. This SDK emits PB signature OIDs even when signing with an
ONB key. The consumer rejects those original mismatched identifiers. Only the
test adapter explicitly changes that unsigned identifier to the ONB OID; both
Go and IIT then verify the unchanged signature value. Modified content fails.
There is no runtime fallback or automatic rewriting of native CMS.
The CMS fuzz target includes ONB173/ONB431 Kupyna-256/512 native seeds in both
their original and explicitly relabeled test forms. A three-minute campaign
with two workers passed 1,352,095 executions after this change.

Twenty unmodified native samples and five disposable GOST certificates are
retained under `internal/cms/testdata/iit-onb-kupyna`, with SDK provenance and
ordinary verification regressions. See the fixture README for reproduction.
This is signature/arithmetic and outgoing-wire evidence, not acceptance of
unmodified native producer output with PB tags on ONB keys.

## Kupyna certificate and CSR signatures

Named ONB certificates and CSRs support Kupyna-256/512 signatures on all five
curves. The subject public-key identifier remains GOST ONB, with legacy named
curve parameters and DKE; the issuer/self-signature has the modern ONB OID.
The issuer's basis determines signature compatibility, independently of the
subject key's algorithm. Inner and outer certificate signature OIDs must agree.

`TestIITModernONBPKI` checks native certificate parsing and key use, exact CSR/SPKI
identity, OpenSSL request parsing, and independent verification of original
TBSCertificate/CRI signatures with unmodified UAPKIC primitives at commit
`1996c0fe56dbbc69f5b00d67784a5bc3033b57fe`. The bounded C test reader explicitly
transcodes the point selector for the reference's legacy decompressor. This is
signature/encoding evidence, not the reference PKIX parser, CA acceptance or trust.
`TestModernONBPKIFixtures` retains all ten public certificate/CSR pairs and checks
wrong keys, wrong basis tags, inconsistent signature identifiers and corruption.
An opt-in replay also verifies independent rejection of modified signed bytes.
See [fixture provenance and reproduction](../internal/testvectors/testdata/modern-onb-pki/README.md).

Probes using modern signature OIDs as the SPKI algorithm, with both legacy and
modern named-curve OIDs, returned IIT certificate parse error 50 and key-read
error 33. Those alternate SPKI profiles remain unsupported; their rejection does
not prevent a modern issuer signature over a GOST ONB subject key.

## Kalyna standard-DH profile

Kalyna-256 CFB and OFB now support explicitly selected standard DH on all five
ONB curves. It uses the non-cofactor agreement OID `1.2.804.2.1.1.1.1.3.8` from
the [national CMS specification](https://zakon.rada.gov.ua/laws/show/z1273-20).
The existing GOST default and PB cofactor profiles remain unchanged. Select the
new profile through the Go API:

```go
options := ua.EncryptionOptions{
    Algorithm: ua.EncryptionKalyna256CFB, // or EncryptionKalyna256OFB
    Agreement: ua.AgreementStandardDH,
    StaticOriginator: true, // optional; embeds the agreement certificate
}
encrypted, err := box.EncryptDocumentWithOptions(data, recipientDER, options)
```

`dstu15946.SharedSecretStandard` validates a nonzero peer in the prime-order
subgroup (`n*Q = O`) before computing `d*Q`, without cofactor multiplication.
Small-order and mixed-order points, infinity, inconsistent domains and out-of-field
coordinates fail. It preserves fixed-width ONB shared-secret encoding for the
Kupyna KDF and national Kalyna key wrap. Fifteen retained vectors from unmodified
Cryptonite `dstu4145_dh(..., false, ...)` independently check the primitive on all
ten PB and five ONB curves. The test adapter is
`pkg/dstu15946/testdata/generate-standard-dh.c`, linked against the pinned
Cryptonite revision used above; ordinary tests need only its JSON output.

The earlier native unwrap mismatch was caused by the provider's agreement scheme:
all five tested ONB curves use `h=1` in its Kalyna output, while it writes the
cofactor-DH identifier ending in `.7`. The PB257 control uses its actual cofactor
of 4. Native decryption accepts correctly encoded standard-DH `.8` output from Go.
The library continues to reject the native ONB producer's mislabeled `.7` data;
it never retries without a cofactor or rewrites a received envelope automatically.

`TestIITStandardDHKalyna` checks both content modes on all five ONB curves plus
PB257, 1/33/65-byte payloads and dynamic, referenced-static and embedded-static
originators (108 Go-to-IIT cases). For native-to-Go checks, only the test adapter
explicitly changes the known `.7` header to `.8`, without altering the native
ciphertext or wrapped key; Go and IIT then decrypt it. Wrong keys and wrapped-key
corruption release no plaintext. Ten unmodified native envelopes, their disposable
certificates and provenance are retained under `internal/cms/testdata/iit-onb-kalyna`.
These fixtures also require rejection of the untouched mislabeled originals.
The complete isolated native regression runner passed with this profile enabled.
Two workers passed three-minute follow-up campaigns: 3,948,444 envelope parsing/
decryption executions and 1,539 signature/agreement executions, the latter now
checking both standard and cofactor DH on all fifteen domains.

## Reproducing operation vectors

With a separate Cryptonite checkout at the pinned revision and a C compiler on
Linux, run from this repository root (the reference source is not a Go dependency):

```sh
ref=/path/to/cryptonite
test "$(git -C "$ref" rev-parse HEAD)" = 3618d340d22e27a6becf97d89c453f8e64068a39 || exit 1
cc -O2 -DCRYPTONITE_EXPORT=extern \
  -I"$ref/src/cryptonite/c" -I"$ref/src/pthread/c" \
  "$ref"/src/cryptonite/c/*.c "$ref"/src/pthread/c/pthread_impl.c \
  pkg/dstu4145/testdata/generate-onb-vectors.c -pthread -lm -o /tmp/onb-vectors
/tmp/onb-vectors > /tmp/onb-operations.json
/tmp/onb-vectors zero > /tmp/onb-zero-digest.json
go test ./pkg/ec ./pkg/dstu4145 ./ua -run 'TestONB' -v
```

Compare decoded JSON fields with the retained fixture; whitespace and property
order do not matter. Ordinary Go tests use the retained public data and require
neither Cryptonite, a C compiler, IIT nor network access.
